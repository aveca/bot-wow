## 3. État du correctif de téléchargement

### Code de la branche par défaut

À la dernière lecture directe de `worker/index.js` sur `main`, le code :
- teste plusieurs clés R2 successivement, y compris `Casinobabe-v1.0.38.zip` en solution de repli ;
- renvoie `404 file_not_found` si aucun objet candidat n’est trouvé ;
- fixe `Content-Disposition` à `Casinobabe-v1.0.38.zip` ;
- incrémente le compteur de téléchargement avant d’avoir confirmé la disponibilité de l’archive et sans réserver le dernier téléchargement de manière atomique.

### PR #19 — correctif plus complet déjà proposé

[PR #19 — fix: never deliver a stale R2 package as the current release](https://github.com/aveca/bot-wow/pull/19)

Branche : `fix/download-artifact-integrity-20261023`  
HEAD vérifié : `0a1a6a5d494a51018684027950688aeb0a8ac988`

La lecture directe de son `worker/index.js` confirme que le correctif proposé :
- accepte uniquement une clé de release versionnée au format `casinobabe-fishing-X.Y.Z.zip` ;
- ne revient pas à une archive historique ;
- renvoie `503 artifact_unavailable` lorsque la clé est invalide ou l’objet absent ;
- ne réserve le téléchargement qu’après avoir trouvé l’objet, avec une mise à jour D1 atomique conditionnée par `count < max_count` ;
- construit le nom transmis dans `Content-Disposition` depuis la clé utilisée.

Le workflow GitHub Actions associé, [run #40070796305](https://github.com/aveca/bot-wow/actions/runs/40070796305), est indiqué comme terminé avec succès. Cela valide le résultat de ce workflow sur ce commit ; cela ne certifie pas les octets R2 et ne prouve pas que le correctif est déployé en production.

Au dernier contrôle, la PR #19 était ouverte, non fusionnée. Il est préférable de l’évaluer plutôt que de créer un correctif concurrent qui duplique ses changements.

### Contradiction à ne pas masquer

La PR #53 rapporte un téléchargement R2 réel, une empreinte SHA-256 de `1c132f367607ea186feffde8bbda0a1a9f94cdec4b7850b93c57c271270bba4f`, une correspondance avec le manifeste et un ZIP de version 1.2.0. Le résultat de P0.5, lui, indique que les octets n’étaient pas accessibles dans l’environnement testé.

Ces affirmations ne sont pas équivalentes et ne doivent pas être fusionnées en une seule conclusion sans retrouver les artefacts et preuves brutes de la PR #53 ou refaire le calcul depuis les octets réels. Cette synthèse ne prétend pas avoir reproduit ce SHA-256.

Les PR #53 et #54 proposent en outre des politiques commerciales incompatibles. Ne pas activer l’achat ni retirer l’avertissement sur la seule base d’une affirmation non reproduite ; choisir une seule politique à partir de preuves vérifiables.

## 6. Décision P0.5 et critères de sortie

**P0.5 est clôturée comme mission de diagnostic. La release v1.2.0 reste non certifiée sur les preuves disponibles dans l’environnement testé.**

Pour modifier ce statut, il faudra au minimum :
1. récupérer les octets réels de `casinobabe-fishing-1.2.0.zip` au moyen d’un accès R2/Wrangler autorisé ;
2. recalculer indépendamment le SHA-256 et le comparer au manifeste attendu ;
3. vérifier la version interne, le manifeste et le contenu du ZIP ;
4. vérifier le code et les tests sur le SHA exact retenu ;
5. vérifier séparément le code réellement déployé avant toute décision de mise en production.

Statuts à distinguer :
- **Objet listé dans R2** : présence constatée par métadonnées ;
- **Archive intégrité vérifiée** : octets obtenus et SHA-256 recalculé ;
- **Correctif vérifié en CI** : tests réussis sur le commit précis ;
- **Production vérifiée** : preuve distincte de la version réellement déployée et du comportement en direct.

Aucun de ces statuts ne doit être substitué à un autre.
