## Executive decision

**Not yet cleared for production deployment.** The original P0/P0.1 claims that the R2 bucket is empty and that four secret *names* are absent are contradicted by the latest Cloudflare API results obtained during this reconciliation. The current facts are:

- The R2 bucket `botwow-binaries` contains two objects, including `casinobabe-fishing-1.2.0.zip`.
- Worker `botwow-api` exists, its settings include the R2 and `RATE_LIMIT` bindings, and `api.bot-wow.com` is associated with it.
- The active Worker code still has a fallback to the historical archive and a hard-coded historical filename.
- The more complete fail-closed download fix is already available in open PR #19. It should be reviewed as the primary code candidate instead of creating a duplicate filename-only patch.
- Presence of secret names is confirmed; values and provider functionality are not confirmed.
- The archive's actual SHA-256 and provenance could not be independently verified from the metadata-only R2 API response available here.
- No KV-reduction change has been measured. PR #19 principally addresses artifact integrity and download-count correctness; it must not be represented as an established KV-quota optimization.

## 3. Code and PR reconciliation

### Current behavior

The Cloudflare-served Worker and GitHub `main` still use this behavior in `handleDownload`:

1. Check the IP rate limit through `RATE_LIMIT`.
2. Validate the download token and license in D1.
3. Check the current download count.
4. Increment the count before checking that the R2 artifact exists.
5. Try the configured key, the hard-coded v1.2.0 key, and the historical `Casinobabe-v1.0.38.zip` fallback.
6. Return the historical filename in `Content-Disposition` regardless of which object was served.

This both permits accidental delivery of an older archive as the current release and means the download allowance can be consumed before artifact availability is established.

### Preferred candidate: PR #19

PR #19 — https://github.com/aveca/bot-wow/pull/19 — is open and not merged. Its branch `fix/download-artifact-integrity-20261023`, HEAD `0a1a6a5d494a51018684027950688aeb0a8ac988`, already proposes the broader correction:

- accept only a versioned configured artifact key;
- do not fall back to the historical archive;
- return `503 artifact_unavailable` if the configured release is missing or invalid;
- check R2 availability before reserving the download count;
- use a conditional atomic D1 update with `count < max_count`;
- derive a safe download filename from the actual configured key;
- add regressions for missing artifacts, historical key rejection, filename correctness, and concurrent download limits.

The associated GitHub Actions run #40070796305 completed successfully. Its job summary lists “Validate static project” and “Run demo and distribution tests” as successful. This is evidence for that workflow run and SHA, not evidence of a live production download or a full end-to-end customer transaction.

PR #44 — https://github.com/aveca/bot-wow/pull/44 — is also open and addresses the filename and checkout-gate behavior, but its download patch is less complete because it retains the fallback behavior and the non-atomic count increment. Avoid merging overlapping download logic blindly.

PR #53 — https://github.com/aveca/bot-wow/pull/53 — says the delivery was verified and recommends correcting the commercial warning. PR #54 — https://github.com/aveca/bot-wow/pull/54 — blocks checkout while delivery is not confirmed. Since the actual v1.2.0 bytes have not been verified here and the live Worker still has the unsafe fallback, the evidence currently does not justify declaring PR #53’s “delivery verified” conclusion proven by this reconciliation. Keep the checkout safety decision conservative until the artifact and delivery path are verified.

## 4. KV quota: what is and is not demonstrated

The source identifies `checkRateLimit(env2.RATE_LIMIT, "download", ip, RATE_LIMITS.download)` as a KV-backed rate-limit call in the download path. This establishes an identified KV usage path, but it does not establish that all such operations are unnecessary or that a proposed change reduces consumption.

PR #19 does not remove or optimize the `RATE_LIMIT` KV path. It corrects download integrity and the D1 allowance reservation; therefore no KV savings percentage is claimed.

No production KV-reduction measurement was obtained during this mission. The earlier “12/12 payment-flow tests” statement refers to a mock-based test result, not Cloudflare's actual operations.

### Post-deployment measurement plan (48–72 hours)

After explicit deployment approval and verification of the exact deployed SHA:

1. Record an agreed pre-change Cloudflare KV baseline or explicitly note if none is available.
2. Record request volume and available Workers/KV read/write metrics over comparable intervals.
3. Segment traffic by endpoint/scenario where the available telemetry supports it.
4. Compare operations per request and total operations, accounting for traffic differences.
5. Report raw metric sources, measurement windows, sample size, and limitations. Do not attribute savings to PR #19 unless a relevant KV-call change has actually been deployed.
